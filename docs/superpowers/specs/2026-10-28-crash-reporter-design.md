# Zbox 崩溃报告与诊断日志设计

## 目标

当 Python 未捕获异常或 Windows 原生致命异常导致 Zbox 退出时，尽量保留可供排查的现场，并通过与现有设置窗一致的双主题弹窗，引导用户把诊断文件提交到 GitHub Issue。

每次崩溃生成：

- 易读、脱敏的 `zbox-crash.log`；
- 可用 WinDbg 分析的 `zbox-crash.dmp`。

不自动上传文件，不改变正常启动、退出和单实例行为。

## 已选方案

采用“进程内捕获 + 独立报告进程”：

1. Python 异常由 `sys.excepthook` 捕获。
2. Windows 原生致命异常由 `SetUnhandledExceptionFilter` 捕获，使用 `MiniDumpNormal` 写最小转储，并保留现有 `faulthandler` 作为文本堆栈兜底。
3. 崩溃进程只尽量保存 `.dmp` 和启动独立报告进程；报告进程整理 `.log` 并显示弹窗，避免继续在已损坏的 GUI 进程中执行界面操作。

不使用常驻调试守护进程，避免长期附加调试器带来的复杂度和行为变化；不启用 WER LocalDumps，避免系统级注册表配置和权限副作用。

极端进程损坏时，进程内转储仍可能失败。任一文件失败不影响另一份文件保存，也不允许崩溃处理触发二次崩溃。

## 文件与目录

每次崩溃使用独立目录：

```text
%APPDATA%\zbox\crash\yyyyMMdd_HHmmss_<pid>\
    zbox-crash.log
    zbox-crash.dmp
```

若同一秒发生冲突，目录名追加短序号，绝不覆盖历史现场。正常退出不生成 `.dmp`，也不显示弹窗。

现有 `crash_native.log` 继续作为 `faulthandler` 的即时输出文件。启动时记录偏移量，报告进程只整理本次启动后追加的内容，避免把历史崩溃混入当前报告。

## 文本日志内容

记录以下诊断信息：

- 报告时间、Zbox 版本、源码/冻结运行形态与架构；
- Python、PySide6、Qt 版本；
- Windows 版本、build 与系统架构；
- Python 异常类型、异常文本与完整堆栈；
- 原生异常代码、异常地址（能够取得时）及本次 `faulthandler` 堆栈；
- 转储和文本报告各自的生成结果或失败原因。

不主动采集用户名、电脑名、IP/MAC、环境变量、配置数据、文件内容、Cookie 或凭据。异常堆栈和异常文本写入前，将用户配置目录及用户主目录替换为 `<UserProfile>`，并脱敏当前用户名。报告正文不写诊断文件的本地绝对路径。

文本日志的脱敏不等于二进制转储脱敏。即使使用 `MiniDumpNormal`，`.dmp` 仍可能包含部分进程内存、模块路径或用户数据，不能承诺完全无敏感信息。弹窗和 Issue 模板必须明确提醒用户在公开提交前自行确认是否附加 `.dmp`。

## 崩溃处理流程

### Python 未捕获异常

1. 创建本次诊断目录，保存异常文本和堆栈。
2. 在当前进程写入 `MiniDumpNormal` 转储。
3. 启动独立 `--crash-reporter` 进程，传入诊断目录与原始异常信息位置。
4. 结束异常实例，不返回 Qt 事件循环继续运行。

### Windows 原生致命异常

1. 在原生异常过滤器中尽量写入 `.dmp`，取得时记录异常代码和地址。
2. 启动独立报告进程，传入诊断目录与本次 `faulthandler` 日志偏移量。
3. 让异常实例终止；报告进程负责后续文本整理和 UI。

原生异常路径不依赖 Qt 事件循环继续存活。捕获回调及其资源必须保持进程级引用，避免被垃圾回收。

## 报告进程与入口

新增 `crash_report.py`（纯标准库）：

- 系统基础信息采集与文本脱敏；
- 独立诊断目录分配；
- 异常文本读取与报告拼装；
- MiniDump 写入与 Windows 原生异常过滤器的底层封装；
- 报告进程命令拼装。

新增 `crash_reporter.py`（Qt）：

- 深浅主题崩溃弹窗；
- 复制完整目录路径；
- 打开诊断目录；
- 打开 GitHub 新 Issue 页面；
- 显示 `.log` / `.dmp` 实际生成结果。

`main.pyw` 在加载正常面板模块及单实例 IPC 之前分派 `--crash-reporter`。报告进程不连接已有实例、不注入桌面菜单、不启动传输、热键或后台任务。

## 弹窗设计

沿用 `#settingsDlg`、`#settingsPanel`、`#setBtn`、`#setSave` 的现有样式，支持 `nocturne` 与 `mica`。左上角窗口图标使用项目真实的 `assets/icon.png`，打包路径沿用现有图标资源规则。

内容包括：

- 标题“程序已崩溃”与简短道歉；
- 诊断文件保存目录及“复制”入口；
- `.log` / `.dmp` 生成状态；
- 文本日志脱敏说明及 `.dmp` 可能包含进程内存的提示；
- 次按钮“打开日志目录”；
- 主按钮“去 GitHub 提交 Issue”；
- 右上角关闭按钮。

界面语言沿用 Zbox 当前语言解析结果，中英文词典键与占位符保持一致。

## GitHub Issue 引导

目标地址为 `https://github.com/evachxji/zbox/issues/new`。通过查询参数预填：

- 标题：`[Crash] Zbox <版本> <异常简述>`；
- 正文：版本、时间、复现步骤占位、文本日志与转储附件清单、`.dmp` 隐私提醒。

不把异常堆栈或日志正文拼进 URL，不自动附加或上传文件。用户自行审查并附加诊断文件。

## 测试与验收

按测试驱动方式先写失败用例，再实现：

1. 系统信息仅包含批准的基础字段，用户目录与用户名被脱敏。
2. 连续报告使用不同目录，历史文件不被覆盖。
3. Python 异常报告包含版本、异常类型、堆栈和原生报告生成状态。
4. 生成的 `.dmp` 存在且以 `MDMP` 文件头开头。
5. Issue URL 不包含日志正文，预填字段和隐私提醒正确。
6. 报告进程不进入单实例转发及正常面板启动流程。
7. 弹窗按钮分别复制路径、打开目录和打开 Issue；深浅主题、真实图标和中英文显示正确。
8. 用独立测试子进程制造受控 Python 异常，验证报告进程接管和文件生成；用受控原生访问冲突验证 `.dmp` 与报告进程接管。
9. 运行现有完整测试集，确认正常启动、退出与现有功能无回归。

验收成功的标准是：两类受控崩溃都能至少留下有效诊断文件并显示独立弹窗；任一文件失败不造成二次崩溃；正常启动和退出不产生崩溃弹窗或 `.dmp`。
